# Korea Web Agent v0.6.1 Core Reliability — Design

Date: 2026-08-25
Status: design approved in chat; implementation not started
Target branch: `design/v0.6.1-core-reliability`

## 1. Purpose

v0.6.1 strengthens the existing Cloud-first shopping research system without replacing the working v0.6.0 architecture.

The primary invariant is:

> A price must not participate in purchase-decision ranking until the system has verified that the offer is the exact requested product, option, size, generation, and required bundle.

Secondary invariants:

> A recommendation must not enter the verified ranking when a user-declared hard requirement is unknown or violated.

> Public price, personalized price, points-adjusted value, conditional payment price, and alternative-condition price must remain semantically separate.

This release is a reliability expansion, not an Action/API redesign.

## 2. Existing architecture to preserve

The following v0.6.0 behavior remains unchanged unless explicitly noted:

- `startProductResearch`
- `getProductResearchResult`
- queued/background Netlify research
- `queued -> running -> completed|partial|failed`
- Cloud research works with the PC offline
- optional authenticated Local Relay enrichment
- Relay Queue v2
- public price history remains separate from personalized Relay price
- request-scoped purchase context only
- existing `BUY / WAIT / SKIP / INSUFFICIENT` decision vocabulary
- existing OpenAPI operation names

No new job architecture, browser extension, VPS migration, or Action operation rename is part of v0.6.1.

## 3. Why v0.6.1 is needed

The concrete failure case is a bundle request such as:

`QWGE43UT1 + EKWBYME78W(V3)`

The current system can find a low price for `QWGE43UT1` while failing to prove that `EKWBYME78W(V3)` is included. Search metadata and partial product identity are currently strong enough to surface a price candidate before the complete bundle identity is verified.

The same structural problem appears in other categories:

- mattress/frame size compatibility
- storage-bed requirements
- monitor refresh-rate/panel variants
- PC builds with exact GPU/RAM/SSD combinations
- appliances sold as body-only vs package
- V2/V3 accessory generations
- new vs refurb/open-box/used alternatives

The fix must therefore be category-independent.

## 4. Selective graft strategy

The attached 0.6.0 design/code is treated as a source of reliability ideas, not as a replacement codebase.

### Adopt

- explicit `same / different / uncertain` philosophy
- deterministic attribute conflict rules
- hard vs significant/minor requirement concept
- shipping unknown must not rank as free
- points are not actual payment
- installment is not a discount
- new-card-only is not an owned-card price
- promotion period validation
- failure taxonomy and manual-action separation
- output validation before delivery
- short-history honesty for price history
- trap-style regression tests

### Do not adopt directly

- alternate Action operation names
- separate parallel orchestration stack
- attached `buildSkuKey()` implementation
- attached payment engine wholesale
- a second retry subsystem
- attached test-count claims as evidence for the live repository
- unrestricted bundle-overlap logic for exact SKU decisions

## 5. Canonical Product Identity

### 5.1 New identity model

Extend the existing `NormalizedTarget` with an internal canonical identity layer rather than overloading `variant`.

Proposed type:

```ts
interface CanonicalProductIdentity {
  kind: 'product';
  brand?: string;
  family?: string;

  primary: {
    model?: string;
    size?: string;
    generation?: string;
    capacity?: string;
    color?: string;
  };

  requiredComponents: CanonicalComponent[];
  optionalComponents: CanonicalComponent[];

  condition: OfferCondition | 'any';
  domesticModel?: boolean;
  installationType?: string;

  source: {
    question: string;
    url?: string;
    confidence: number;
  };
}

interface CanonicalComponent {
  type: string;
  model?: string;
  version?: string;
  quantity?: number;
  aliases?: string[];
}
```

### 5.2 Example

For `QWGE43UT1 + EKWBYME78W(V3)`:

```text
brand: WIDEVU
primary.model: QWGE43UT1
primary.size: 43
requiredComponents:
  - type: mobile_stand
    model: EKWBYME78W
    version: V3
condition: new
```

The system may still expose the simpler `NormalizedTarget` externally for backward compatibility. Canonical identity is an internal reliability object used by matching, verification, history, Relay merge, and validation.

## 6. Identity comparison model

Replace binary eligibility assumptions with an explicit comparison result:

```ts
type IdentityVerdict =
  | 'exact'
  | 'same_except_condition'
  | 'uncertain'
  | 'different';
```

### 6.1 Exact

All required identity fields that are known in the canonical target are positively verified in the candidate.

### 6.2 Same except condition

Everything required for product identity matches, and only `condition` differs.

This is the only verdict allowed to enter `alternativeCondition` ranking.

### 6.3 Uncertain

No contradictory decisive attribute exists, but at least one required identity field is not verified.

Examples:

- TV model matches but stand model is absent
- stand is mentioned but version is absent
- frame is `K` but usable internal length is not stated

Uncertain candidates can be shown as preliminary but cannot become decisive price winners.

### 6.4 Different

Any known decisive attribute conflicts:

- V2 vs V3
- 43 vs 50 inch
- body-only vs required bundle
- 1600x2000 vs required 1670x2075
- different component model

A different candidate is excluded regardless of text similarity score.

## 7. Required component gate

Current loose bundle heuristics are insufficient for exact-product research. v0.6.1 introduces an all-of required-component gate.

For every `requiredComponents[]` item:

- matching component type alone is insufficient
- if canonical model is known, candidate model must match
- if canonical version is known, candidate version must match
- missing required model/version => `uncertain`
- explicit mismatch => `different`

Search-friendly aliases may help discovery but cannot override conflicting canonical fields.

## 8. Hard Constraint Engine

### 8.1 Requirement classes

```ts
type RequirementStrength = 'hard' | 'soft';

type ConstraintVerification =
  | 'verified_pass'
  | 'verified_fail'
  | 'unknown';
```

Each product-recommendation request compiles into:

```ts
interface ProductConstraint {
  id: string;
  label: string;
  strength: RequirementStrength;
  operator: string;
  expected: unknown;
  source: 'user' | 'resolved_identity';
}
```

### 8.2 Ranking gate

- all hard constraints `verified_pass` => eligible
- any hard constraint `unknown` => preliminary
- any hard constraint `verified_fail` => excluded

Soft constraints affect scoring only.

### 8.3 Example: bed frame

User requirement:

- mattress 1670x2075x360
- storage drawers required
- headless or sofa-style headboard

Compiled hard constraints:

- supported width >= 1670
- supported length >= 2075
- drawer storage = true
- headboard style in {headless, sofa}

A product with `K` in its name but no verified usable dimensions cannot rank as BUY.

## 9. Provider pipeline redesign

The existing public-search provider remains usable for discovery, but decisive pricing is split into four stages.

```text
DISCOVER -> IDENTIFY -> VERIFY -> EXTRACT
```

### 9.1 Discover

Goal: find candidate URLs.

Inputs:

- canonical identity
- market-specific query template
- user constraints where useful

Outputs:

- search hits only
- no final ranking eligibility

### 9.2 Identify

For each candidate, parse identity evidence from title/snippet/URL.

Output:

- identity verdict
- matched canonical fields
- missing canonical fields
- conflicting canonical fields

Only `exact` or sufficiently promising `uncertain` candidates move to direct verification.

### 9.3 Verify

Fetch the actual product page when technically and legally accessible.

Verify:

- product title
- option/variant
- required bundle contents
- dimensions/specs relevant to hard constraints
- sale state / stock state
- price
- shipping
- seller/merchant when available

### 9.4 Extract

Only after verification, normalize an offer.

The offer records field provenance so that identity, price, shipping, and payment can have independent verification levels.

## 10. Verification policy

Keep the existing public verification vocabulary for compatibility:

- `checkout_verified`
- `page_verified`
- `search_metadata`
- `unverified`

Add ranking policy:

### Decisive new-product cash winner requires

- identity verdict = `exact`
- hard constraints = all verified pass
- verification >= `page_verified`
- shipping known
- sale not ended / out of stock
- condition = new or explicitly accepted by the user

`search_metadata` can produce a preliminary candidate but cannot produce the decisive cash winner for an exact-product price-sensitive request.

## 11. Market coverage v2: Provider Attempt Ledger

Replace opaque `no_match` reporting with staged coverage.

Proposed internal record:

```ts
interface ProviderAttempt {
  market: string;
  attemptedAt: string;
  completedAt?: string;

  discovery: {
    attempted: boolean;
    hitCount: number;
  };

  identity: {
    exact: number;
    uncertain: number;
    different: number;
  };

  verification: {
    attempted: number;
    succeeded: number;
    failed: number;
  };

  offers: {
    extracted: number;
    eligible: number;
  };

  failureKind?: FailureKind;
  failureMessage?: string;

  status:
    | 'verified'
    | 'found_unverified'
    | 'no_match'
    | 'failed'
    | 'not_attempted';
}
```

External `marketCoverage` remains backward-compatible but is derived from this ledger.

This distinction is important:

- zero search hits => `no_match`
- candidate found but identity unverified => `found_unverified`
- exact candidate but page blocked => `failed`
- exact page verified and eligible offer extracted => `verified`

## 12. Failure model integration

Do not create a second retry engine. Extend the existing retry/failure model with semantic failure kinds:

- captcha
- login_required
- rate_limited
- network_transient
- blocked_by_site
- not_found
- region_required
- stock_check_required
- parse_failed
- relay_offline

Policy examples:

- `rate_limited`: bounded automatic backoff
- `network_transient`: bounded automatic backoff
- `captcha`: no automatic bypass; manual check
- `login_required`: no public retry loop; Relay/manual path
- `blocked_by_site`: limited retry, then failed coverage
- `not_found`: no retry; valid no-match outcome
- `parse_failed`: one bounded parser retry/fallback, then partial result

Failure records feed both `marketCoverage` and `manualChecks`.

## 13. Offer eligibility model

Extend `MarketOffer` internally with:

```ts
identityVerdict: IdentityVerdict;
constraintStatus: 'eligible' | 'preliminary' | 'excluded';
fieldVerification: {
  identity: OfferVerification;
  price: OfferVerification;
  shipping: OfferVerification;
  payment?: OfferVerification;
};
```

`eligible` remains available for backward compatibility but is derived from these fields.

### New-product ranking

Only exact + hard-pass candidates participate.

### Alternative-condition ranking

Only `same_except_condition` candidates participate.

A cheap used/refurb listing of a different model/version cannot become `alternativeCondition`.

## 14. Price history redesign

### 14.1 Canonical history key

History keys must come from the canonical target, not each seller's wording.

Example:

```text
WIDEVU:QWGE43UT1:43:STAND-EKWBYME78W:V3:NEW
```

### 14.2 History recording gate

Record a public observation only when:

- identity = exact
- verification >= page_verified
- condition = new
- shipping known
- total public cash price known
- source is public, not personalized Relay

### 14.3 History honesty

Preserve the current rolling six-month behavior, with explicit:

- actual observation window
- sample count
- source distinction
- no “all-time low” unless the data really supports it

If retained history is short, return `insufficient` or low-confidence wording.

## 15. Relay identity-safe merge

Authenticated Relay enrichment gets a second identity check.

Flow:

```text
Cloud exact candidate URL
-> Relay open
-> re-read page identity
-> compare against canonical identity
-> if exact: merge personalized fields
-> if uncertain/different: reject personalized merge
```

This prevents a login session or option selector from silently switching to another variant.

Personalized prices never enter public history.

## 16. Purchase context safety

Keep request-scoped purchase context only.

Return an explicit field:

```ts
purchaseContextApplied: {
  ownedCards: string[];
  paymentMethods: string[];
  memberships: string[];
  budget?: number;
  region?: string;
  preferences: string[];
}
```

Rules:

- no backend persistent profile
- no automatic restoration of old card/membership assumptions
- final presentation may only call a condition “user-specific” if it appears in `purchaseContextApplied`
- publicly advertised payment conditions remain separate from owned-card pricing

## 17. Payment invariants adopted in v0.6.1

Do not replace the whole payment engine yet. Add and test these invariants:

1. points do not reduce actual payment
2. installment is not a discount
3. unknown shipping cannot rank
4. new-card-only cannot rank as owned-card
5. expired promotion cannot apply
6. minimum-spend requirements must be satisfied
7. conditional payment remains separate from owned-card pricing

Full PaymentOption v2 and stacking-rule expansion is deferred to v0.6.2 unless required by a concrete regression.

When PaymentOption v2 is introduced, IDs must be namespaced by market/offer to avoid cross-market collision.

## 18. Response validator

Introduce a server-side validation pass before final decision/presentation.

Minimum blocker codes:

- `IDENTITY_INCOMPLETE_IN_WINNER`
- `HARD_CONSTRAINT_UNKNOWN_IN_WINNER`
- `HARD_CONSTRAINT_FAILED_IN_WINNER`
- `SEARCH_METADATA_AS_DECISIVE`
- `UNKNOWN_SHIPPING_IN_WINNER`
- `ALTERNATIVE_SKU_MISMATCH`
- `PERSONALIZED_IDENTITY_MISMATCH`
- `HISTORY_IDENTITY_MISMATCH`
- `UNOWNED_CARD_IN_OWNED_RANKING`
- `POINTS_AS_CASH`
- `EXPIRED_PROMOTION`
- `MARKET_COVERAGE_INCONSISTENT`
- `PURCHASE_CONTEXT_NOT_APPLIED`

If any blocker affects the decisive evidence, the response cannot return a confident BUY based on that evidence.

The system should degrade to `INSUFFICIENT` when evidence is incomplete rather than manufacture a ranked winner.

## 19. Presentation layer

Add an optional server-generated presentation while preserving structured fields.

```ts
interface ProductReport {
  // existing structured fields...
  presentation?: {
    markdown: string;
    sections?: Record<string, string>;
  };
}
```

Default presentation order for price-sensitive research:

1. decision + resolved exact identity
2. actual cash payment
3. owned-card price
4. public conditional payment price
5. effective/member scenarios
6. alternative condition
7. price history
8. market coverage
9. Relay state
10. limitations/manual checks

The GPT should prefer server presentation for the first result, while still being able to answer follow-up questions from structured data.

## 20. Logging and safety lint

Adopt the useful static safeguards from the attached design, adapted to the existing logging layer:

- request body/payload must not be passed directly to console logging
- sensitive values must flow through existing redaction helpers
- `shippingFee ?? 0` style ranking shortcuts are forbidden when they convert unknown shipping into free shipping

Do not replace the current logging implementation.

## 21. Regression test matrix

Implementation must be test-first.

Mandatory cases:

### Exact bundle identity

- QWGE43UT1 body-only vs QWGE43UT1 + EKWBYME78W(V3)
- V2 vs V3
- 43 vs 50 inch
- generic “stand included” but missing stand model/version => uncertain
- explicit wrong component model => different

### Hard constraints

- 1670x2075 required vs 1700x2000 => excluded
- drawer storage unknown => preliminary
- verified drawer + verified dimensions + valid head style => eligible
- only two verified products exist => return Top 2, do not pad Top 5
- zero verified products => INSUFFICIENT

### Offer eligibility

- shipping null => not decisive
- search metadata price only => preliminary
- page-verified exact offer => decisive candidate
- out-of-stock exact offer => excluded from current winner

### Alternative condition

- exact same SKU refurb => alternative allowed
- different model used item => alternative forbidden

### Payment

- points never reduce actual cash payment
- installment not treated as discount
- expired promotion rejected
- new-card-only separated from owned card
- conditional public payment separated from owned-card ranking

### Price history

- seller wording changes but canonical identity stays same => one history series
- body-only price cannot enter bundle history
- personalized Relay price cannot enter public history
- short window does not become “all-time low”

### Relay

- public result survives Relay offline
- Relay exact identity => personalized merge allowed
- Relay changed variant => merge rejected

### Coverage

- zero hits => no_match
- hits but no exact candidate => found_unverified/no_match according to evidence
- exact candidate but page blocked => failed
- exact page verified => verified

### Async compatibility

- queued -> running -> completed
- queued -> running -> partial
- failed worker returns terminal failed
- existing operation IDs remain unchanged

## 23. Rollout strategy

- exact/uncertain/different/same-except-condition

- offer eligibility

### Phase 2 — Provider depth

### Deferred

- Browser Extension
- VPS/AWS migration

## 24. Acceptance criteria

v0.6.1 is acceptable when all of the following are true:

1. `QWGE43UT1` body-only price can never be reported as the decisive price for `QWGE43UT1 + EKWBYME78W(V3)`.
2. Missing `EKWBYME78W` or `V3` produces `uncertain`, not `exact`.
3. A different used/refurb product cannot become `alternativeCondition`.
4. A hard requirement that is unknown prevents verified recommendation ranking.
5. Search metadata alone cannot produce the decisive exact-product cash winner.
6. Market coverage explains whether failure happened in discovery, identity, verification, or extraction.
7. Price history uses canonical identity and cannot mix body-only, other version, or personalized prices.
8. Relay personalized data is merged only after identity re-check.
9. User-specific card/membership claims appear only if they were actually applied in the request.
10. Existing Action operation names and async polling continue to work.
11. Existing full repository test suite passes, plus the new regression matrix.
12. Production build and typecheck pass before merge.

## 25. Non-goals

This release does not aim to guarantee access to every Korean commerce site. Anti-bot controls, login requirements, regional inventory, and dynamic checkout conditions remain external constraints.

The goal is instead:

> when the system cannot verify a decisive fact, it must represent that uncertainty accurately and refuse to promote the candidate into a stronger claim than the evidence supports.
