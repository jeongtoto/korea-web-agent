# Korea Web Agent v0.6.2 Provider Coverage Design

## Status

Approved design for the v0.6.2 Cloud Provider Coverage release.

## Goal

Upgrade Korea Web Agent from broad search plus limited page verification into a hybrid provider system that can discover exact products across major Korean commerce channels, follow comparison-site offers to actual seller pages, verify identity, price, shipping, promotion state, and availability, and only then admit a public offer into decisive cash-price ranking.

The release must preserve the v0.6.1 Core Reliability rules. v0.6.2 improves acquisition and market coverage; it does not weaken identity, hard-constraint, shipping, history, Relay, or response-validation gates.

## Primary User Outcome

For an exact product such as:

`와이드뷰 QWGE43UT1 + EKWBYME78W(V3)`

v0.6.2 should move beyond:

`다나와 표시가 449,000원 -> 배송비 미확인 -> INSUFFICIENT`

and, when public evidence permits, reach:

`가격비교 페이지 -> 실제 판매처 URL -> exact bundle -> sale price -> shipping -> stock -> totalCashPrice -> decisive verified offer`

A lower search snippet, stale time deal, similar bundle, or price-comparison advertisement must never beat a fully verified seller-page offer.

## Architectural Choice

### Selected approach: Hybrid Provider Adapters

Retain the generic discovery path as a fallback and add market-specific adapters for high-value Korean commerce channels.

The architecture becomes:

```text
Generic Discovery / Provider Discovery
                ↓
        Canonical Identity
                ↓
          Market Adapter
                ↓
       Seller Expansion
        (when required)
                ↓
       Direct Verification
                ↓
      Checkout Economics
                ↓
         Offer Dedupe
                ↓
         Best Offers
                ↓
     Response Validator
                ↓
        Presentation
```

This avoids two undesirable extremes:

- keeping the current generic-search-only approach, which cannot reliably prove seller shipping and final checkout economics;
- fully rewriting every market as a standalone crawler, which would create excessive maintenance and release risk.

The generic static HTML / JSON-LD parser remains a fallback under market-specific extractors.

---

## Core Invariants Carried Forward from v0.6.1

These rules are non-negotiable:

```text
search_metadata != decisive price
comparison-site advertised price != verified seller cash price
shipping unknown != free shipping
similar bundle != exact bundle
expired promotion != current deal
personalized price != public cash price
public history != personalized history
```

A decisive new-condition cash offer requires:

- `identityVerdict = exact`
- all explicit hard constraints verified eligible
- seller/direct page verification for price
- known mandatory shipping cost or provable free shipping
- available/purchasable state
- active or non-promotional price state
- no unresolved mandatory charge that changes total cash outlay

No provider may bypass these conditions to improve market coverage or fill a Top N list.

## Provider Interface

Each market adapter implements a common contract.

Conceptually:

```ts
interface MarketProvider {
  discover(...): Promise<DiscoveryCandidate[]>;
  identify(...): IdentityAssessment;
  expandSellers?(...): Promise<SellerCandidate[]>;
  verify(...): Promise<VerifiedCandidate>;
  extractOffer(...): Promise<NormalizedOffer | null>;
}
```

Not every provider needs every stage.

Examples:

- Coupang usually verifies its own product page and does not need seller expansion.
- Danawa and Enuri are comparison providers, so `expandSellers()` is central.
- Naver may discover a Shopping listing and then follow the listing to the actual seller page when needed.
- Kakao TalkDeal and Toss Shopping require promotion/public-visibility semantics in addition to ordinary price verification.

The orchestrator must consume all providers through one common result shape and must not embed retailer-specific ranking logic.

## Proposed Module Boundaries

### New focused modules

```text
src/providers/
├─ market-provider.ts
├─ provider-registry.ts
├─ seller-expansion.ts
├─ shipping.ts
├─ promotion.ts
├─ offer-dedupe.ts
└─ markets/
   ├─ naver.ts
   ├─ coupang.ts
   ├─ danawa.ts
   ├─ enuri.ts
   ├─ elevenst.ts
   ├─ gmarket.ts
   ├─ auction.ts
   ├─ ssg.ts
   ├─ lotteon.ts
   ├─ himart.ts
   ├─ official.ts
   ├─ kakaotalkdeal.ts
   └─ toss-shopping.ts
```

### Responsibilities

`market-provider.ts`
- shared provider interfaces
- common normalized candidate/result shapes
- provider budget contract

`provider-registry.ts`
- registers the 13 required providers
- selects applicable providers
- exposes deterministic order/metadata without forcing serial execution

`seller-expansion.ts`
- converts comparison/shopping portal listings into seller candidates
- preserves discovery provenance
- never upgrades an advertised comparison price into a decisive seller offer

`shipping.ts`
- normalizes free, paid, conditional-free, and unknown shipping
- computes mandatory shipping when deterministically knowable
- never interprets unknown or seller-inquiry shipping as zero

`promotion.ts`
- normalizes time deals and public promotional conditions
- detects active, expired, future, and unknown promotion state
- prevents expired deals from decisive ranking

`offer-dedupe.ts`
- merges the same economic seller offer discovered through multiple sources
- preserves all discovery provenance
- prevents confidence inflation from duplicate portal paths

`markets/*`
- market-specific discovery and extraction semantics
- no final ranking authority

## Existing Modules to Modify

### `src/orchestrator/provider-pipeline.ts`

Current flow:

```text
public search
-> promising candidates
-> top 3 direct pages
-> offers
```

Target flow:

```text
provider discover
-> canonical identify
-> optional seller expansion
-> direct seller verification
-> shipping/promotion normalization
-> normalized offers
-> request-scoped dedupe
```

The v0.6.1 canonical identity and constraint engines remain authoritative.

### `src/providers/direct-page.ts`

The current JSON-LD/static parser stays as a generic fallback.

Preferred acquisition order:

```text
market-specific extractor
-> generic structured data / JSON-LD
-> static page metadata
```

A market-specific extractor may improve field extraction, but must not weaken URL safety, redirect safety, size limits, read-only behavior, or identity verification.

### `src/core/types.ts`

Only additive fields are introduced. Existing fields remain for backward compatibility.

Candidate additions include:

```ts
shipping?: {
  status: 'free' | 'paid' | 'conditional_free' | 'unknown';
  baseFee?: number;
  threshold?: number;
  verification: VerificationLevel;
  remoteAreaExtraUnknown?: boolean;

promotion?: {
  type: 'time_deal' | 'public_coupon' | 'instant_discount' | 'none';
  startsAt?: string;
  endsAt?: string;
  active: boolean | 'unknown';
};

seller?: {
  name?: string;
  productId?: string;
  canonicalUrl?: string;

  identity?: FieldProvenance;
  price?: FieldProvenance;
  shipping?: FieldProvenance;
  availability?: FieldProvenance;
};
```

Existing `shippingFee`, `salePrice`, and `totalCashPrice` remain available to current consumers.

## Market-Specific Verification Rules

### Naver Shopping

Verify:
- exact product/variant identity
- seller/store identity
- sale price
- mandatory shipping
- purchasable/stock state when exposed

When a Naver Shopping result is a portal listing rather than the final seller page, follow to the actual seller page before using it as a decisive cash offer.

### Coupang

Verify:
- exact product and option/variant
- sale price
- public shipping semantics
- availability/purchasable state

Account-only WOW or personalized benefits are not public cash offers in v0.6.2.

### Danawa

Role: comparison + seller expansion.

Flow:

```text
exact comparison product page
-> extract seller candidates
-> follow actual seller URLs
-> reverify exact SKU/bundle
-> verify sale price + shipping + availability
-> construct verified seller offers
```

Danawa advertised prices remain discovery metadata until seller verification succeeds.

### Enuri

Same semantics as Danawa.

### 11st / Gmarket / Auction

Verify:
- exact option/SKU/bundle
- sale price
- shipping
- seller identity
- availability

Public payment conditions may be represented separately, but account-specific or saved-wallet personalization is excluded.

### SSG

Verify:
- exact product/option
- online sale price
- shipping/store fulfillment condition
- availability

A price that depends on an unresolved store, pickup, or delivery condition must not be presented as an unconditional total cash price.

### LotteON / Lotte Hi-Mart

Verify:
- model and bundle
- sale price
- shipping/delivery condition
- availability

Installation or mandatory appliance delivery fees must be included when deterministically known, otherwise represented as unresolved cost risk.

### Official Store

Official-store discovery should identify the verified brand/manufacturer domain rather than hard-code one global store.

Purpose:
- canonical model/bundle reference
- official list/sale price
- shipping
- warranty/A/S reference
- authoritative product identity baseline

Official price need not be the cheapest to be useful.

### Kakao TalkDeal

Verify public-only fields:
- exact identity
- seller
- public deal price
- deal type
- start/end timestamps when exposed
- active/expired state
- shipping
- availability

Expired deals are historical evidence only.

Friend-only/account-only benefits are deferred to v0.6.3.

### Toss Shopping

Verify public/shareable fields only:
- exact product identity
- public price
- shipping
- seller
- promotion state
- availability

If the apparent price requires login, account state, app-only personalization, or otherwise cannot be proven publicly, mark it `found_unverified` or conditional evidence rather than a decisive public price.

## Seller Expansion

Comparison and shopping portals may discover the same downstream seller offer.

Use a dedicated `SellerCandidate` shape conceptually similar to:

```ts
interface SellerCandidate {
  discoveredFrom: string;
  comparisonUrl?: string;
  sellerName?: string;
  sellerUrl: string;
  advertisedPrice?: number;
  advertisedShipping?: number;
  canonicalIdentity?: CanonicalProductIdentity;
}
```

`advertisedPrice` is not a decisive price.

Only after direct seller verification may the candidate become a verified `MarketOffer`.

Discovery provenance must remain attached so a final offer can state that it was discovered by Danawa, Enuri, Naver, or generic search but verified at the seller page.

---

## Field-Level Provenance

Each decisive economic field should retain where it was verified.

Conceptually:

```ts
provenance: {
  identity: { sourceUrl, method, verifiedAt },
  price: { sourceUrl, method, verifiedAt },
  shipping: { sourceUrl, method, verifiedAt },
  availability: { sourceUrl, method, verifiedAt }
}
```

This allows legitimate mixed provenance, for example:

- identity strongly confirmed by an official product page;
- seller price verified on 11st;
- seller discovered through Danawa.

However, final offer eligibility is still determined from the actual seller/product evidence required by the v0.6.1 identity and response-validation gates.

---

## Shipping Model

Replace the implicit “number or unknown” interpretation with explicit semantics.

```ts
shipping.status =
  | 'free'
  | 'paid'
  | 'conditional_free'
  | 'unknown'
```

### `free`

Shipping cost is explicitly zero/free for the relevant order.

### `paid`

A deterministic mandatory fee is known.

`totalCashPrice = salePrice + baseFee + other known mandatory charges`

### `conditional_free`

Free shipping depends on a deterministic threshold/condition.

If the current exact-product purchase itself satisfies the condition, shipping may be resolved as zero.

If the condition cannot be proven, decisive total cash price remains unresolved.

### `unknown`

Includes situations such as:
- 착불
- 지역별 상이 with unresolved amount
- 판매자 문의
- shipping omitted entirely
- mandatory installation/delivery charge not deterministically known

Unknown never defaults to zero.

### Additional mandatory costs

When relevant and publicly known, include mandatory:
- installation fees
- delivery fees
- handling fees

Potential remote-area/floor-carry extras that cannot be known from the request remain explicit risk flags rather than silently assumed zero.

---

## Promotion Model

Normalize public promotions separately from unconditional cash price.

```ts
promotion.type =
  | 'time_deal'
  | 'public_coupon'
  | 'instant_discount'
  | 'none'

promotion.active = true | false | 'unknown'
```

Rules:

- expired promotion: never decisive
- future promotion: not current winner
- active public promotion: may compete in the appropriate public-conditional ranking
- unknown validity: preliminary/conditional, not decisive
- account-only promotion: excluded from v0.6.2 public winner semantics

---

## Offer Dedupe

The same seller offer may be discovered through Danawa, Enuri, Naver, and generic web search.

Deduplicate by the strongest available combination of:

- seller canonical URL
- seller identity
- seller product ID
- canonical product key
- offer condition

Example:

```text
Danawa -> 11st seller A
Enuri  -> 11st seller A
Naver  -> 11st seller A
```

must become one economic offer, not three independent verified offers.

Preserve:

```text
discoveredBy:
- danawa
- enuri
- naver

verifiedAt:
- 11st seller page
```

This prevents false confidence inflation and duplicate market-price rows.

## Global Time Budget and Concurrency

Target total Cloud research budget: approximately 40–50 seconds.

Suggested phase allocation:

```text
Discovery              8–10s
Identity/Expansion     8–10s
Direct verification   20–25s
Normalize/validate      3–5s
```

Initial concurrency limits:

```text
Discovery concurrency        5
Direct verification          4
Seller expansion verify      3
Same-domain concurrency      1–2
```

One slow or blocked provider must not monopolize the global job.

The guiding principle is:

`partial trustworthy evidence > whole-job timeout`

Provider-level timeouts and failures are recorded in coverage rather than aborting the entire research job.

---

## Request-Scoped Verification Cache

Use a request-scoped cache keyed by canonicalized seller URL so the same downstream seller page is fetched only once per research job even if multiple discovery sources point to it.

Benefits:
- fewer duplicate requests
- lower latency
- lower risk of CAPTCHA/rate limit
- consistent field extraction across duplicate discovery paths

No persistent cross-request web cache is required for v0.6.2.

---

## Failure Isolation

Each provider returns bounded provider state independently.

Provider-level statuses remain compatible with the v0.6.1 coverage model:

```text
verified
found_unverified
no_match
failed
not_attempted
```

Failure kinds include the existing semantic taxonomy, such as:

```text
captcha
login_required
rate_limited
network_transient
blocked_by_site
not_found
region_required
stock_check_required
parse_failed
unknown
```

Example:

```text
Coupang        failed / blocked_by_site
Naver          verified
Danawa         verified
TalkDeal       no_match
Toss Shopping  found_unverified
```

must still produce a valid terminal public result from the verified markets.

Whole-job `failed` should be reserved for system-level failure such as orchestrator corruption, state-store failure, or invariant violation.

## Ranking Semantics

### Unconditional public cash winner

A candidate may enter `bestOffers.cash` only when:

```text
identityVerdict = exact
constraintStatus = eligible
condition = new
price verification >= page_verified
shipping is resolved
availability is purchasable
promotion is active or absent
all mandatory total-cash charges are resolved
```

Rank by:

`totalCashPrice = salePrice + mandatory shipping + known mandatory charges`

### Public conditional winner

Publicly available but conditional economics should remain separate from unconditional cash.

Examples:
- active Kakao TalkDeal price
- public coupon available to any buyer
- public instant payment-method discount
- deterministic minimum-purchase promotion

A new `bestOffers.publicConditional`-style surface may be added additively if implementation confirms it is the cleanest compatibility path.

It must never be merged into `bestOffers.cash` merely because the numeric price is lower.

### Personalized/account-only pricing

No public provider may manufacture or infer this in v0.6.2.

If proof requires login or user account state, defer to Relay/personalization rather than upgrading the price.

---

## Decision Semantics

`INSUFFICIENT` must not mean “all 13 markets were not perfectly verified.”

Decision quality is based on decisive evidence, not raw coverage count.

A BUY may be possible when only a subset of markets are verified if the exact product and public economics are sufficiently proven and the response validator has no blockers.

Example:

```text
Naver      verified
11st       verified
Danawa     verified via seller expansion
Coupang    blocked
TalkDeal   no_match
Toss       found_unverified
```

may still yield a valid decisive offer.

Conversely:

```text
13 markets contain many numeric prices
but zero exact seller offers have resolved shipping
```

must remain `INSUFFICIENT`.

## Market Coverage Presentation

Coverage should become more diagnostic without changing the core status vocabulary.

Useful provider details include:

```text
Naver Shopping
status: verified
exactOffers: 2

Coupang
status: failed
failureKind: blocked_by_site

Danawa
status: verified
comparisonPages: 1
expandedSellers: 5
eligibleSellers: 2

Kakao TalkDeal
status: no_match

Toss Shopping
status: found_unverified
reason: shipping unknown
```

The server-side presentation should summarize these facts rather than claiming complete-market certainty.

---

## Public Price History Interaction

v0.6.1 history safety remains unchanged.

Only decisive public cash observations that satisfy canonical identity, direct verification, new condition, and known shipping may enter public price history.

Comparison-site advertisements, search snippets, stale promotions, account-only values, and unverified shipping do not seed history.

Deduped downstream seller offers should create one observation, not one per discovery path.

Existing terminal fields, `canonicalIdentity`, `validationWarnings`, `purchaseContextApplied`, `bestOffers`, `marketCoverage`, and `presentation` remain backward compatible.

## Security and Policy Requirements

All existing safety constraints remain in force:

- read-only commerce research
- no purchase mutations
- no checkout submission
- no login credential collection
- no cookie/token return
- SSRF protection for public URLs
- safe redirect handling
- bounded HTML size
- bounded retries
- explicit domain/market extraction logic
- no CAPTCHA bypass
- no secret-bearing logs

Market-specific adapters must use the same core URL and redaction policies rather than reimplementing weaker variants.

## Testing Strategy

### Existing regression floor

All existing v0.6.1 tests remain mandatory. The current release baseline is 245 passing tests, but implementation must treat the actual full suite at the time of merge as the success criterion rather than hard-code a fixed count.

### Shared provider contract tests

Every market adapter fixture must pass common invariants:

- exact identity is preserved
- search-only price cannot become decisive
- unknown shipping cannot become decisive cash
- expired promotion cannot become decisive
- unavailable product cannot become decisive
- seller provenance is preserved
- provider failure remains isolated
- account-only value is never represented as public cash

### Required integration regressions

At minimum:

1. Danawa advertises 449,000 KRW, downstream seller verifies exact bundle + free shipping -> decisive cash 449,000.
2. Danawa advertises 439,000 KRW, seller shipping remains unknown -> 439,000 is not decisive.
3. Naver and Danawa discover the same 11st seller item -> one deduped economic offer.
4. Kakao TalkDeal 350,000 KRW expired -> historical/non-decisive only.
5. Kakao TalkDeal 379,000 KRW active, exact, free shipping -> eligible public deal.
6. Toss Shopping 369,000 KRW requires unresolved account state -> not decisive public cash.
7. Coupang blocked while Naver/11st verify -> whole research does not fail.
8. Exact seller pages exist but all shipping remains unknown -> final decision remains INSUFFICIENT.
9. Only a subset of the 13 markets verify, but a decisive exact total-cash offer is valid -> BUY remains possible.
10. Search snippet shows 330,000 KRW but actual seller verifies 399,000 KRW -> 330,000 never wins.
11. Danawa and Enuri both expand to the same seller URL -> seller is fetched once within the request-scoped cache.
12. Duplicate discovery paths do not inflate confidence or public price-history observation count.

### Exact-product release smoke test

Use:

`와이드뷰 QWGE43UT1 + EKWBYME78W(V3)`

Verify:
- Action start and polling remain functional
- canonical bundle identity remains exact
- all 13 provider attempts are represented or explicitly not attempted for deterministic reason
- Danawa/Enuri seller expansion executes when applicable
- unknown shipping never enters decisive cash ranking
- a seller-verified total cash price enters best offers when available
- lower search metadata cannot override seller verification
- Relay being offline does not prevent public Cloud research

## Implementation Order

Implementation should proceed incrementally, not by editing all 13 adapters at once.

Recommended sequence:

```text
1. Provider contract + registry
2. Shipping + promotion + offer dedupe
3. Request-scoped verification cache
4. Danawa + Enuri seller expansion
5. Naver + Coupang
6. 11st + Gmarket + Auction
7. SSG + LotteON + Hi-Mart
8. Official-store provider
9. Kakao TalkDeal + Toss Shopping
10. Orchestrator integration
11. Action/OpenAPI additive fields if required
12. E2E + release smoke tests
```

Each behavior change should follow TDD: add a failing regression/contract test, confirm RED, make the smallest implementation change, then confirm GREEN before moving on.

## Deployment Strategy

Implement on an isolated branch derived from the verified v0.6.1 `main` branch.

Suggested implementation branch:

`feature/v0.6.2-provider-coverage`

Before merge, verify at minimum:

```text
npm ci
npm audit --omit=dev --audit-level=high
npm test
npm run typecheck
npm run build
```

Then run the exact-product Action smoke test against the deploy candidate.

Do not merge or promote to production if any v0.6.1 reliability regression appears.

---

## Rollback Strategy

Provider v2 must remain separable from v0.6.1 Core Reliability.

The system should retain a bounded legacy generic-provider path so the provider registry can fall back to the previous generic pipeline when necessary during rollout.

Rollback must preserve:

- canonical identity
- hard-constraint gating
- search-metadata exclusion from decisive ranking
- unknown-shipping exclusion
- canonical public history safety
- Relay identity-safe merge
- response-validator blockers
- deterministic presentation

A Provider v2 failure must never require rolling back the v0.6.1 safety layer.

---

## Release Success Definition

v0.6.2 is complete when the Cloud path can, for the 13 required domestic channels, discover exact products, follow comparison portals to downstream sellers when needed, verify seller-page identity/price/shipping/availability/promotion state, deduplicate duplicate seller offers, and rank only verified total-cash economics without weakening any v0.6.1 safety invariant.

In one sentence:

> Across 13 Korean shopping channels, only an exact seller offer with verified public price, mandatory shipping, and purchasable state may become a decisive current-price winner; all lower-quality or personalized-looking numbers remain explicitly non-decisive.
