# v0.7 Shopping Intelligence — Precision Research Design

Date: 2026-08-26
Status: Proposed design approved in chat; implementation requires this written spec review
Branch: `feature/v0.7-shopping-intelligence`
Base: `main` / v0.6.2

## 1. Purpose

Korea Web Agent (KWA) must answer broad shopping questions such as:

- “퀸 사이즈에 맞는 가성비 사계절 차렵이불 추천해줘.”
- “50만원 이하 43인치 4K 이동식 TV 추천해줘.”

The system must do more than find the cheapest listing. It must discover a broad market, normalize product families/variants/bundles, verify hard requirements, compare product quality and reviews, verify current purchase economics for finalists, and explain why a recommendation is good value.

The existing v0.6.2 Provider v2 system remains the exact-product purchase verification engine. v0.7 adds a recommendation/intelligence layer above it rather than expanding the exact-product pipeline into a monolith.

## 2. Primary design principles

1. **Cloud-first recommendation.** Public web/cloud research must produce a useful recommendation without the local PC Relay.
2. **Relay isolation.** Relay may refine personalized purchase economics, but Relay availability must not alter public product-quality ranking.
3. **Broad discovery, strict final verification.** Candidate discovery favors recall; final recommendations and decisive prices favor precision.
4. **Hard constraints are gates, not score penalties.** A product that fails a required constraint cannot win by being cheap.
5. **Recommendation score and confidence are separate.** A product can look excellent but still have weak evidence.
6. **Evidence provenance is mandatory.** Every material claim in the final Top 5 must map to evidence.
7. **No single confidence number controls the entire recommendation.** Missing shipping or personalization must degrade only the relevant dimension.
8. **Complexity must be bounded.** New subsystems use narrow interfaces and staged budgets; v0.6.2 behavior remains regression-protected.
9. **No dependency expansion without measured benefit.** New open-source dependencies are introduced only after fixtures/benchmarks show the current parser or matcher is insufficient.
10. **Precision over unsupported certainty.** Unknown remains unknown; the system must not infer a decisive fact from search metadata or vague text.

## 3. Scope

### 3.1 In scope for v0.7.0

- Query planning for `EXACT_PRODUCT`, `COMPARISON`, and `RECOMMENDATION` modes.
- Broad recommendation discovery producing 20–50 normalized candidates when the market has sufficient coverage.
- Category-aware hard constraints, soft preferences, and evaluation axes.
- Initial Golden Categories:
  - `portable_display`
  - `bedding`
- Candidate normalization and duplicate clustering.
- Light enrichment of 12–20 candidates.
- Deep research of up to 5 finalists.
- Review/quality evidence normalization.
- Value/Fit scoring independent from evidence confidence.
- Reuse of v0.6.2 exact-price verification for finalists.
- Stage/progress diagnostics compatible with existing `queued/running/completed/partial/failed` jobs.
- Golden Scenario tests and v0.6.x regression gates.

### 3.2 Explicitly out of scope for v0.7.0

- Hosting Chromium/Playwright inside the main Netlify production runtime.
- A separate Python recommendation service.
- A vector database.
- A new external LLM API dependency.
- Full support for every shopping category.
- Allowing Relay-only data to determine the public recommendation winner.
- Treating fuzzy matching as final product identity proof.

## 4. Existing architecture to preserve

The following v0.6.2 components remain authoritative for exact-product verification:

- `src/orchestrator/research.ts`
- `src/orchestrator/provider-pipeline.ts`
- `src/providers/provider-registry.ts`
- `src/core/canonical-identity.ts`
- `src/core/offer-engine.ts`
- `src/providers/offer-dedupe.ts`
- `src/report/product-report.ts`
- Relay protocol/security boundary
- Action start/poll contract:
  - `POST /api/agent/research`
  - `GET /api/agent/job?jobId=...`

v0.7 must call these through explicit interfaces instead of moving recommendation logic into them.

## 5. High-level pipeline

```text
User query
  -> Query Planner
  -> Broad Discovery
  -> Product Normalizer
  -> Hard Constraint Gate
  -> Light Enrichment
  -> Preliminary Ranking
  -> Deep Research (Top 5)
  -> Exact Price Verification (v0.6.x)
  -> Value/Fit Ranking
  -> Final Top 5
  -> Optional Relay personalized economics overlay
```

Target funnel:

```text
30–80 raw hits
  -> 20–50 normalized candidates
  -> 12–20 eligible/light candidates
  -> 8–10 preliminary shortlist
  -> 5 deep-research finalists
  -> 3–5 final recommendations
```

The numbers are targets, not reasons to fabricate coverage. If the market yields fewer valid products, the response must state the actual counts.

## 6. New subsystem boundaries

Create a new `src/shopping/` domain. Each module must have one primary responsibility.

### 6.1 `query-planner.ts`

Input: natural-language query + purchase context.

Output: `ShoppingResearchPlan`.

Responsibilities:
- classify mode;
- infer category;
- parse hard constraints;
- parse soft preferences;
- parse budget;
- select category schema;
- generate bounded discovery queries;
- assign stage budgets.

It must not fetch web pages or rank products.

### 6.2 `category-registry.ts`

Owns category schemas and evaluation dimensions.

Initial schemas:

#### `portable_display`
Hard/structured fields may include:
- screen size;
- resolution;
- portable/mobile stand requirement;
- budget;
- required smart features when explicitly requested.

Default evaluation dimensions:
- fit: 20
- display quality: 20
- mobility/stand: 15
- smart features: 10
- build/durability: 10
- service/warranty: 10
- review consensus: 5
- value: 10

#### `bedding`
Hard/structured fields may include:
- size/bed compatibility;
- type (comforter/quilt/set) when required;
- budget;
- seasonality when explicitly required.

Default evaluation dimensions:
- fit: 15
- fabric/fill quality: 20
- tactile comfort: 15
- seasonal comfort: 15
- care/washing: 10
- durability: 10
- allergy/safety: 5
- review consensus: 5
- value: 5

Weights are normalized at runtime. User priorities may reweight soft dimensions but may not override a hard constraint gate.

### 6.3 `discovery.ts`

Performs broad, query-fan-out discovery.

Properties:
- multiple category-aware query variants;
- provider/site diversification;
- per-query hit caps;
- global raw-hit cap;
- no direct decisive recommendation;
- search metadata is discovery evidence only.

Discovery must not call all 13 exact-price providers for every candidate.

### 6.4 `candidate-normalizer.ts`

Converts raw hits into `ShoppingCandidate` groups.

Identity hierarchy:

```text
product family
  -> model
    -> variant
      -> bundle
        -> seller offer
```

Rules:
- model/variant/bundle conflicts prevent merging;
- fuzzy/lexical similarity may propose a cluster but never prove identity;
- exact model identifiers dominate title similarity;
- bundle components remain separately represented;
- condition differences remain separate from new-product candidates.

### 6.5 `constraint-gate.ts`

Evaluates the plan’s hard constraints using structured facts.

States:
- `ELIGIBLE`
- `PRELIMINARY` (required fact unknown)
- `EXCLUDED` (verified hard-constraint failure)

A verified failure is permanent for that candidate/variant in the job.

### 6.6 `light-enrichment.ts`

Adds bounded evidence to 12–20 candidates:
- one official/manufacturer/spec source when available;
- 1–3 public price signals;
- review coverage count/availability;
- brand/service/warranty signal;
- structured Product/Offer facts.

Light-enrichment prices are not automatically decisive purchase prices.

### 6.7 `deep-research.ts`

Runs only for up to five finalists.

Minimum evidence plan per finalist, where available:
- official/manufacturer specification;
- current retailer detail page;
- independent user review evidence;
- negative/defect query;
- long-term/durability query;
- service/warranty evidence.

Deep research explicitly searches for downside evidence to reduce positive-selection bias.

### 6.8 `review-intelligence.ts`

Normalizes review-like evidence into structured signals.

`ReviewEvidence` fields:
- candidate key;
- topic;
- polarity;
- source class;
- verified purchase status when known;
- sponsored status when known;
- publication/retrieval time;
- source URL;
- independence key;
- confidence.

Example topics:
- `display_quality`
- `stand_stability`
- `speaker_quality`
- `fabric_softness`
- `washing_durability`
- `dust_shedding`
- `service_quality`

Rules:
- duplicated/reposted claims do not linearly increase confidence;
- sponsored evidence may inform facts but cannot independently create HIGH review confidence;
- star rating alone cannot determine quality score;
- a negative topic requires independent/repeated evidence before becoming a major penalty unless an authoritative defect/recall source exists.

### 6.9 `price-verification-adapter.ts`

Bridges finalists to existing v0.6.x Provider v2.

Default budget:
- Top 5: targeted high-value providers (Naver, Coupang, Danawa, Enuri, official when applicable).
- Top 3: full required Provider v2 coverage.
- Expand positions 4–5 to full coverage if:
  - score margin to Top 3 is <= 5 percentage points;
  - Top 3 public cash price confidence is insufficient;
  - fewer than two finalists have verified public cash offers.

The exact-price engine remains authoritative for decisive seller economics.

### 6.10 `ranking.ts`

Produces two separate outputs:

1. `recommendationScore` — how good the product appears for the user.
2. `evidenceConfidence` — how strongly the available evidence supports that score.

Recommendation score is built from category dimensions plus normalized price advantage within a comparable cohort.

Price comparison cohort must contain only candidates that satisfy the same hard product requirements. A cheaper but non-compliant product cannot boost its rank.

### 6.11 `shopping-orchestrator.ts`

Coordinates stages and budgets.

It must not contain provider-specific parsing or category-specific scoring constants.

Responsibilities:
- execute stages;
- store progress;
- enforce maximum counts/time budgets;
- isolate per-source/per-candidate failures;
- produce partial but useful results when non-critical stages fail.

## 7. Core data contracts

Introduce explicit types rather than overloading `ProductCandidate`.

### 7.1 `ShoppingResearchPlan`

```ts
interface ShoppingResearchPlan {
  mode: 'EXACT_PRODUCT' | 'COMPARISON' | 'RECOMMENDATION';
  categoryId: string;
  budget?: { max: number; strength: 'hard' | 'soft' };
  hardConstraints: ShoppingConstraint[];
  preferences: ShoppingPreference[];
  dimensionWeights: Record<string, number>;
  discoveryQueries: DiscoveryQuery[];
  limits: ShoppingStageLimits;
}
```

### 7.2 `ShoppingCandidate`

```ts
interface ShoppingCandidate {
  key: string;
  family?: string;
  brand?: string;
  model?: string;
  variant?: Record<string, string | number | boolean>;
  bundle?: string[];
  condition: OfferCondition;
  title: string;
  sourceUrls: string[];
  facts: Record<string, FactValue>;
  constraintState: 'ELIGIBLE' | 'PRELIMINARY' | 'EXCLUDED';
}
```

Every structured fact must retain provenance and verification state.

### 7.3 `CandidateAssessment`

Contains:
- category scores;
- recommendation score;
- confidence dimensions;
- strengths;
- tradeoffs;
- negative signals;
- evidence references;
- verified/public price status;
- exclusion reasons.

## 8. Confidence model

Do not use a single weighted average to decide whether recommendation research is valid.

Expose dimensions such as:
- identity;
- hard constraints;
- official specs;
- review consensus;
- negative coverage;
- price verification;
- durability evidence;
- service/warranty;
- personalization.

Critical gates:
- a finalist with a verified hard-constraint failure cannot be recommended;
- a decisive public cash offer requires v0.6.x price eligibility;
- Relay offline sets `personalization=unavailable` but does not reduce public quality/fit confidence;
- unknown shipping reduces price confidence only;
- missing durability evidence reduces durability/review confidence only.

Overall display confidence may be derived for presentation, but must not be used as a substitute for the dimension gates.

## 9. Recommendation decision semantics

For recommendation mode, `INSUFFICIENT` is reserved for systemic insufficiency, such as:
- no candidates satisfying the user’s hard constraints;
- unresolved category/constraint interpretation severe enough to make ranking unsafe;
- finalists lacking enough product identity evidence;
- virtually no independent quality evidence for any finalist.

The following alone must not make the whole recommendation `INSUFFICIENT`:
- Relay offline;
- one candidate’s shipping fee unknown;
- no personalized coupon;
- one retailer blocked;
- one candidate lacking a long-term review.

Instead these become per-dimension limitations.

## 10. Relay contract

Public recommendation ranking is computed before Relay personalization.

Relay may produce `personalizedPurchaseScenario` for finalists:
- account coupons;
- owned-card discounts;
- memberships;
- logged-in prices;
- account-specific shipping/points.

Rules:
- Relay values never enter public price history;
- Relay offline never changes public recommendation order;
- a personalized price may create a separate “best deal for your account” order, clearly labeled;
- identity must still match the finalist before Relay economics are accepted.

## 11. Job progress model

Keep existing terminal API statuses for backwards compatibility.

Add optional internal/presentation fields:

```ts
stage:
  | 'PLANNING'
  | 'DISCOVERY'
  | 'NORMALIZATION'
  | 'LIGHT_ENRICHMENT'
  | 'DEEP_RESEARCH'
  | 'PRICE_VERIFICATION'
  | 'RANKING'
  | 'COMPLETE'

progress: {
  rawHits?: number;
  normalizedCandidates?: number;
  eligibleCandidates?: number;
  deepResearchCompleted?: number;
  deepResearchTotal?: number;
  priceVerificationCompleted?: number;
  priceVerificationTotal?: number;
}
```

The Action start/poll interface remains unchanged.

## 12. Runtime and work budgets

The system must remain bounded even in precision mode.

Initial defaults:
- raw discovery hits: max 80;
- normalized candidates: max 50;
- light enrichment: max 20;
- preliminary shortlist: max 10;
- deep research: max 5;
- full 13-provider verification: normally max 3, conditionally max 5;
- per-source retries follow existing retry policy;
- per-provider failure is isolated.

The orchestrator stops lower-value work when enough evidence is already available to preserve runtime budget.

## 13. Open-source dependency policy

Potential tools:
- Cheerio for robust static HTML traversal;
- Fuse.js for non-authoritative clustering assistance;
- Crawlee/Playwright as future browser-worker options;
- Mozilla Readability as future article-body extraction option.

Adoption gates:
1. create a failing fixture/benchmark demonstrating a concrete deficiency;
2. measure whether the dependency materially improves extraction/matching;
3. check package size/security/runtime impact;
4. verify no regression in existing tests;
5. keep product identity and recommendation policy in KWA-owned code.

v0.7.0 begins with existing dependencies. Cheerio/Fuse.js are added only if the TDD fixture proves they are needed.

## 14. Golden fixtures and scenarios

### 14.1 `TV-001`

Query: “50만원 이하 43인치 4K 이동식 TV 가성비 좋은 거 추천해줘. 화질과 이동성이 중요해.”

Must verify:
- 4K hard constraint;
- screen-size compatibility;
- mobile stand requirement;
- multiple product families;
- wrong/FHD SKUs cannot win;
- public recommendation works with Relay offline;
- Top 5 carry quality/review/price evidence;
- exact-price verification runs only after shortlisting.

### 14.2 `BEDDING-001`

Query: “퀸 사이즈 사계절 차렵이불, 고급스러운 디자인, 세탁 편하고 30만원 이하로 가성비 추천해줘.”

Must verify:
- Queen-size compatibility as a hard constraint;
- seasonality/type compatibility;
- washability and textile/fill quality as category dimensions;
- a cheaper wrong-size item cannot rank;
- review evidence is independent and topic-normalized;
- final recommendation explains quality/value tradeoff, not only price.

## 15. Mandatory regression scenarios

1. FHD is cheaper than 4K when 4K is required -> FHD cannot enter final Top 5.
2. S/Q mixed bedding page -> only verified Queen variant can satisfy Queen requirement.
3. Wrong SKU is substantially cheaper -> cannot become decisive price winner.
4. Ten duplicated copies of one review -> review confidence does not materially inflate.
5. Sponsored-only positive reviews -> review confidence cannot reach HIGH.
6. Shipping unknown -> quality/fit confidence remains unchanged; price confidence degrades.
7. Relay offline -> public ranking remains identical.
8. Relay online -> only personalized purchase scenario may differ.
9. Exact URL revalidation -> weaker search metadata cannot downgrade a stronger exact identity without conflicting page evidence.
10. Search metadata price -> never becomes decisive purchase winner.
11. One provider failure -> other providers/candidates continue.
12. v0.6.2 exact-product WideView E2E remains green.

## 16. Release gates

v0.7.0 cannot merge unless all conditions are satisfied:

- hard-constraint violating products in final Top 5: 0;
- wrong-SKU decisive price winners: 0;
- search-metadata decisive winners: 0;
- duplicate-review confidence inflation: 0 material regressions in golden fixtures;
- Relay-offline public ranking changes: 0;
- unsupported material claims in golden final recommendations: 0;
- Top 5 material claims with evidence provenance: 100%;
- `TV-001` E2E: pass;
- `BEDDING-001` E2E: pass;
- existing v0.6.x full test suite: pass;
- typecheck: pass;
- production build: pass;
- production dependency audit: pass;
- no committed secrets/generated dist artifacts.

## 17. Implementation sequencing

Implementation must be incremental and continuously green.

1. Add data contracts + Query Planner tests.
2. Add Category Registry + hard constraint tests.
3. Add broad Discovery with deterministic fixture tests.
4. Add Candidate Normalizer + identity/duplicate regression tests.
5. Add Light Enrichment.
6. Add Review Intelligence and independence tests.
7. Add Deep Research planner/executor.
8. Add ranking + decomposed confidence.
9. Add v0.6.x Price Verification Adapter.
10. Add Shopping Orchestrator and progress state.
11. Integrate Action recommendation path while preserving exact-product path.
12. Add Golden `TV-001` and `BEDDING-001` E2E.
13. Run full v0.6.x regression + security/build checks.
14. Open Draft PR; do not merge until all release gates are green and explicitly approved.

Each step must use TDD: add a failing test first, implement the smallest change, then run targeted and full regression checks at defined checkpoints.

## 18. Anti-complexity rules

To prevent the new system from degrading existing functionality:

- `src/orchestrator/research.ts` remains the exact-product research pipeline; do not turn it into the shopping recommendation orchestrator.
- Category rules live only in `category-registry.ts`/category-specific definitions.
- Provider-specific extraction remains under `src/providers/`.
- Review topic parsing does not modify provider price eligibility.
- Recommendation ranking does not mutate `MarketOffer`.
- Relay code does not participate in public recommendation scoring.
- No module may both fetch sources and define category scoring policy.
- No module may both cluster identity and declare decisive seller economics.
- New dependencies require a fixture-backed justification.
- If a module grows beyond one clear responsibility, split before adding more behavior.

## 19. Rollout strategy

v0.7 initially runs recommendation mode only for the two Golden Categories. Exact-product and unsupported-category requests retain v0.6.x behavior.

Recommended rollout:
1. deterministic fixture tests;
2. shadow comparison on Golden Scenarios;
3. Draft PR CI;
4. deploy preview smoke;
5. explicit merge approval;
6. production smoke;
7. live Action E2E for TV and bedding recommendation queries.

If a recommendation-mode regression appears after deployment, the system must be able to route recommendation requests back to the existing v0.6.x path without changing the exact-product contract.

## 20. Definition of done

v0.7.0 is done when KWA can answer the two Golden recommendation queries by:

- discovering a broad market;
- showing actual candidate counts;
- enforcing hard requirements;
- deeply researching five finalists;
- separating quality/value score from confidence;
- explaining recurring strengths and weaknesses with evidence;
- verifying final purchase economics through v0.6.x;
- operating usefully without Relay;
- optionally overlaying Relay-personalized economics;
- passing every release gate with no v0.6.x regression.
