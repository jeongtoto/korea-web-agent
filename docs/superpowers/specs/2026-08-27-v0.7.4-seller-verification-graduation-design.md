# v0.7.4 Seller Verification Graduation — Design

Status: Design approved in chat; implementation pending written-spec review.

## 1. Goal

Increase the rate at which a discovered exact product price can be promoted into a decisive public cash offer without weakening v0.7.3 safety rules.

The target failure mode is the current pattern:

1. a comparison page identifies the exact SKU/bundle and an advertised price,
2. the comparison page does not expose a decisive shipping total,
3. the system fails to reach or verify the actual seller page,
4. the offer remains non-decisive and the research result becomes `INSUFFICIENT`.

v0.7.4 must improve seller-page reachability and verification depth, not relax evidence requirements.

## 2. Success Criteria

A comparison-page candidate can graduate to a decisive offer only when all of the following are verified on a current seller page or trusted seller-domain structured payload:

- exact product identity,
- exact required bundle/variant,
- current public sale price,
- mandatory shipping charge or explicit free shipping,
- current availability is not explicitly unavailable,
- mandatory purchase fees are resolved when a mandatory-fee signal exists,
- product condition when material to the request.

The decisive total is:

`publicCashTotal = salePrice + mandatoryShipping + mandatoryPurchaseFees`

Unknown values are never replaced with zero.

### 2.1 Evidence authority

For v0.7.4, a `trusted seller-domain structured payload` means structured product/offer data fetched from the canonical seller domain through the same public-URL and provenance path as a direct seller page. It does **not** include comparison-site metadata, search snippets, cached search cards, or redirect query parameters.

A fallback-discovered page is eligible for seller verification only if the fetched page itself exposes retailer/product facts sufficient for the existing direct-page identity and offer checks. A blog, forum, price-history page, or search result page cannot graduate merely because its text contains the model and a price.

## 3. Non-goals

v0.7.4 does not:

- weaken exact identity or bundle gates,
- treat search metadata as decisive price evidence,
- infer free shipping from absence of a shipping label,
- let comparison-page advertised price override a newer seller-page price,
- let Relay-personalized prices mutate public ranking/history,
- add broad browser automation to every market,
- expand recommendation categories,
- change v0.7.3 recommendation-tier semantics.

## 4. Current Architecture and Failure Point

Current comparison providers follow this flow:

`public search -> comparison page -> extract seller links -> seller page -> verifiedSellerOfferFromPage()`

The main weakness is seller resolution. Static anchor extraction works when the comparison page exposes attributable `<a href>` elements, but many Korean commerce pages represent seller targets in embedded JSON, data attributes, redirect/bridge URLs, script payloads, or dynamically rendered structures.

When seller resolution fails, the comparison page itself may still provide an exact bundle and advertised price, but shipping remains unresolved. v0.7.3 correctly refuses to promote that offer.

## 5. Proposed Architecture

Introduce an explicit seller-resolution pipeline between comparison-page verification and seller-page verification.

`Comparison Page`

`-> Stage 1: Static seller links`

`-> Stage 2: Embedded seller metadata`

`-> Stage 3: Redirect/bridge resolution`

`-> Stage 4: Exact-identity fallback seller discovery`

`-> Seller candidate normalization/deduplication`

`-> Seller page verification`

`-> Exact identity + bundle + price + shipping + availability + mandatory fees`

`-> VERIFIED decisive offer`

Stages are ordered. Later stages are fallback mechanisms, not parallel authority sources.

## 6. New Components

### 6.1 `seller-resolution.ts`

Single responsibility: produce normalized seller candidates from a verified comparison page.

Inputs:

- comparison-page URL,
- raw page HTML or parsed page result,
- exact canonical identity,
- provider ID,
- request time/budget.

Outputs:

- normalized seller candidates,
- resolution method,
- source URL,
- optional advertised price/shipping metadata,
- trace events.

It must not decide whether an offer is decisive.

### 6.2 `seller-redirect.ts`

Single responsibility: safely resolve comparison-site redirect/bridge URLs into a final seller URL.

Rules:

- follow only HTTP/HTTPS,
- reuse public-URL policy/SSRF protection,
- maximum 5 redirect hops,
- reject unsupported schemes,
- preserve original comparison URL in provenance,
- do not treat redirect query parameters alone as verified offer facts.

### 6.3 `seller-fallback-discovery.ts`

Single responsibility: when comparison-derived candidates do not yield any seller page that can enter direct verification, run a tightly scoped exact-identity seller search.

Query construction must include the strongest available identity fields:

- brand,
- exact model,
- exact variant/bundle token,
- seller-market terms only when useful.

Fallback results are discovery candidates only. They must pass the same direct seller-page verification path before becoming offers.

## 7. Seller Resolution Stages

### Stage 1 — Static anchors

Retain current `extractComparisonSellerLinks()` behavior.

Improvements are limited to deterministic extraction of attributable seller metadata already present in HTML attributes/text.

### Stage 2 — Embedded metadata

Parse seller targets from deterministic page data such as:

- JSON script blocks,
- serialized page-state objects,
- `data-*` attributes,
- structured seller arrays,
- explicit outbound URL fields.

Requirements:

- only deterministic parsing; no LLM extraction,
- extract URL plus seller/product identifiers when available,
- advertised price/shipping remain indicative until seller-page verification,
- malformed blocks are ignored without crashing the provider.

### Stage 3 — Redirect/bridge resolution

If a candidate URL points to a comparison-site bridge/redirect endpoint, resolve it before seller verification.

Requirements:

- maximum 5 redirects,
- every hop must pass public-URL validation,
- final URL must be HTTP/HTTPS,
- redirect loops/failures isolate only that seller candidate,
- final seller host becomes the canonical seller market identity.

### Stage 4 — Exact-identity fallback discovery

Run only when stages 1–3 produce no seller page that can enter direct verification. A comparison-derived candidate that fails to fetch, resolves back to a comparison page, or lacks retailer/product offer facts does not suppress fallback discovery.

The fallback search must be exact-product focused and capped by provider budget.

A fallback search hit cannot become decisive from title/snippet alone. It must be fetched and re-verified as a seller page.

## 8. Candidate Deduplication and Priority

Seller candidates are deduplicated by canonicalized final URL plus seller product ID when present.

Priority order:

1. direct seller URL from comparison structured metadata,
2. direct seller URL from static attributable link,
3. resolved bridge/redirect URL,
4. exact-identity fallback search result.

If the same seller appears through multiple paths, provenance records all discovery paths but verification is performed once through the shared verification cache.

## 9. Seller-page Verification Contract

The existing decisive offer gate remains strict.

An offer is eligible only if:

- identity verdict is exact,
- required constraints are eligible,
- shipping is known,
- availability is not explicitly unavailable,
- mandatory purchase fees are resolved when applicable.

### Price authority

Seller-page current price is authoritative over comparison-page advertised price.

If they differ, record a discrepancy trace:

- comparison advertised price,
- seller verified price,
- absolute/relative delta,
- seller page retrieval time.

The comparison price is never substituted back into the decisive offer.

### Shipping authority

Shipping can be verified from:

- trusted seller-domain structured offer payload,
- deterministic seller-specific extractor,
- unambiguous visible seller-page text.

Absence of shipping text means `unknown`, not zero.

### Mandatory fees

Add an explicit optional `mandatoryPurchaseFee` for unavoidable charges separable from shipping, such as mandatory installation/delivery surcharges when the item cannot be purchased without them.

Fee applicability is deterministic:

- `required` when the seller page/structured payload explicitly states that a fee/service is mandatory for purchase or fulfillment,
- `not_applicable` when no mandatory-fee signal is present,
- `unknown` when a mandatory-fee signal is present but its amount cannot be resolved.

Only `required` contributes to `publicCashTotal`. `unknown` blocks decisiveness. `not_applicable` contributes zero by definition; this rule does not apply to shipping, whose absence remains `unknown`.

Optional installation, extended warranty, membership, or elective services must not be included in public cash total.

## 10. Data Contract Additions

All additions are backward-compatible optional fields; v0.7.4 does not remove existing `MarketOffer` or `SellerCandidate` fields.

### Seller resolution method

`static_link | embedded_metadata | redirect_resolution | fallback_search`

### Mandatory fee status

`required | not_applicable | unknown`

### Verification trace

Each seller candidate records a structured trace sufficient to explain why it did or did not graduate.

Minimum fields:

- comparisonSource,
- comparisonUrl,
- resolutionMethod,
- originalSellerUrl,
- resolvedSellerUrl,
- identityVerdict,
- bundleVerdict,
- priceStatus,
- shippingStatus,
- availabilityStatus,
- mandatoryFeeStatus,
- comparisonAdvertisedPrice,
- sellerVerifiedPrice,
- mandatoryPurchaseFee,
- totalCashPrice,
- rejectionReasons,
- retrievedAt.

Trace is diagnostic/provenance data. It does not independently override offer eligibility.

## 11. Market Scope

Primary v0.7.4 comparison-market targets:

- Danawa,
- Enuri,
- Naver Shopping comparison/product pages where applicable.

The architecture is generic, but implementation should avoid adding market-specific heuristics unless a deterministic fixture or production sample justifies them.

Retail seller verification continues to use existing direct-page and market-specific extractors.

## 12. Error Handling

Failures are candidate-local.

- one malformed embedded block does not fail the comparison provider,
- one redirect failure does not discard other seller candidates,
- one seller fetch failure does not discard verified sellers,
- fallback search failure leaves the original comparison offer non-decisive,
- unknown shipping remains non-decisive,
- exact-identity conflict immediately rejects that seller offer,
- a mandatory-fee signal with unresolved amount remains non-decisive.

The system must preserve an explicit reason when graduation fails.

## 13. Performance and Budgets

The resolution pipeline must remain bounded.

- reuse existing provider seller-expansion budgets,
- cap embedded candidates before network verification,
- resolve only candidates within budget,
- use verification cache to avoid duplicate seller fetches,
- fallback search runs only after comparison-derived seller verification cannot proceed,
- no unbounded crawling.

Browser automation is not part of the default v0.7.4 path.

A later browser fallback is permitted only as a separately approved change backed by benchmark evidence that deterministic methods are insufficient.

## 14. Public vs Personalized Isolation

Public seller verification remains independent of Relay.

Relay may provide logged-in coupon/card/member overlays after the public decisive offer is determined.

Relay state must never change:

- public seller resolution order,
- public identity verdict,
- public shipping status,
- public total cash price,
- public winner/history.

## 15. Output Semantics

v0.7.3 recommendation/output synchronization remains unchanged.

v0.7.4 may improve `INSUFFICIENT` into a decisive result only by producing additional verified seller evidence.

If no seller graduates, output remains `INSUFFICIENT` and should expose the dominant verification gap, for example:

- `seller_resolution_failed`,
- `seller_identity_mismatch`,
- `shipping_unknown`,
- `availability_unresolved`,
- `mandatory_fee_unknown`.

Do not replace these with a generic confidence percentage alone.

The Action may expose a compact verification summary derived from the trace, but raw internal fetch data and secrets are never exposed.

## 16. Golden Benchmarks

### G1 — Static seller link success

Danawa exact `QWGE43UT1 + EKWBYME78W(V3)` page exposes a direct attributable seller link. The system reaches seller page and verifies exact bundle, price, and shipping.

### G2 — Embedded seller URL success

No usable seller anchor exists, but an embedded deterministic payload contains the seller URL. The seller is extracted and verified.

### G3 — Redirect/bridge success

Comparison page exposes a bridge URL. The bridge safely resolves to a seller page; final seller URL is verified.

### G4 — Wrong bundle rejection

Comparison page says V3 but final seller page is V2 or TV body only. Offer is rejected and never decisive.

### G5 — Seller price overrides comparison price

Comparison page advertises 399,000 KRW but seller page currently shows 429,000 KRW. Decisive price uses 429,000 KRW and discrepancy is recorded.

### G6 — Shipping included in total

Seller page shows 389,000 KRW + mandatory 20,000 KRW shipping. Decisive public cash total is 409,000 KRW.

### G7 — Unknown shipping remains insufficient

Exact seller page and price are verified but shipping cannot be determined. Offer remains non-decisive; no zero inference.

### G8 — Search metadata cannot win

A 365,400 KRW search snippet is cheaper than verified offers but has no verified seller page. It cannot become the decisive winner.

### G9 — Fallback discovery graduation

Comparison page has no usable seller data. Exact-identity fallback search finds a current retailer seller page; after full verification it may become decisive.

### G10 — Relay isolation

Relay online/offline produces identical public seller resolution, public winner, public price, and verification trace.

### G11 — Candidate failure isolation

One redirect loop and one malformed embedded payload do not prevent a third valid seller candidate from becoming decisive.

### G12 — Mandatory fee handling

A seller page explicitly marks installation as mandatory but does not expose the amount. Offer remains non-decisive with `mandatory_fee_unknown`. An optional installation add-on does not affect public cash total.

### G13 — WideView production benchmark

Production Action for `QWGE43UT1 + EKWBYME78W(V3)` must surface a compact seller-resolution verification summary and either:

- produce at least one decisive seller offer with exact bundle + shipping total, or
- remain `INSUFFICIENT` with a precise terminal verification gap showing exactly where seller graduation failed.

The benchmark does not permit manufacturing a decisive result merely to satisfy the test.

## 17. Regression Invariants

All v0.7.1–v0.7.3 invariants remain mandatory:

- wrong SKU never decisive,
- wrong bundle never decisive,
- unknown shipping never decisive,
- search metadata never decisive,
- seller-page current facts outrank stale comparison metadata,
- Relay personalized price never contaminates public ranking/history,
- Relay availability never changes public recommendation order,
- exact-product requests remain on exact verification path,
- recommendation tiers remain synchronized with final output wording.

## 19. Complexity Guardrails

- seller resolution does not decide recommendation ranking,
- redirect resolution does not parse product specs,
- fallback discovery never promotes snippets directly,
- direct seller verification remains the decisive authority,
- market-specific parsing stays isolated behind extractors,
- no circular imports,
- no external runtime service or LLM dependency,
- no new browser-runtime requirement,
- every heuristic must have a deterministic fixture/test.

- typecheck passes,

- production WideView benchmark does not violate decisive-offer gates.

## 21. Release Outcome

The desired behavioral change is not “return BUY more often.”

It is:

> reach more real seller pages, verify more complete public purchase totals, and therefore convert only genuinely verified candidates from `INSUFFICIENT` into decisive offers.
