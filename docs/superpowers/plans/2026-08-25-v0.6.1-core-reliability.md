# Korea Web Agent v0.6.1 Core Reliability Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Prevent partial/mismatched product offers from entering purchase-decision rankings by adding canonical bundle identity, hard-constraint gating, direct-page verification, staged market coverage, identity-safe history/Relay merging, and server-side response validation.

**Architecture:** Preserve the current v0.6.0 Cloud-first queued/background Action pipeline and add a reliability layer around the existing resolver, provider search, offer engine, price history, Relay merge, and report builder. Search metadata becomes discovery evidence only; decisive offers require exact canonical identity, all hard constraints verified, page-level verification, known shipping, and valid availability. Public history and authenticated Relay enrichment remain separate.

**Tech Stack:** Node.js >=22, TypeScript 5.8.3, built-in `node:test`, `@netlify/blobs` 10.7.13, Netlify Functions/Background Functions, existing Local Relay.

**Spec:** `docs/superpowers/specs/2026-08-25-v0.6.1-core-reliability-design.md`

## Global Constraints

- Preserve `startProductResearch` and `getProductResearchResult`; do not rename Action operations.
- Preserve `queued -> running -> completed|partial|failed` and the existing Background Function job engine.
- Preserve Cloud-first behavior when the PC/Relay is offline.
- Preserve Relay Queue v2; do not replace queue architecture.
- Purchase context remains request-scoped only; no persistent card/membership profile.
- Personalized Relay prices must never enter public price history.
- `search_metadata` may surface preliminary candidates but may not be the decisive exact-product cash winner.
- Unknown shipping must never be treated as zero/free for ranking.
- Any unknown hard constraint makes a candidate preliminary; any failed hard constraint excludes it.
- `alternativeCondition` requires the same canonical product with condition as the only decisive difference.
- No new runtime dependency is required for v0.6.1.
- Use the repository test style: `node:test` + `node:assert/strict`.
- Before final merge run `npm test`, `npm run typecheck`, `npm run build`, and `npm audit --omit=dev --audit-level=high`.
- The previously verified functional head had 184 passing tests; do not hard-code that count as a success condition. The current full suite must pass and the new regression tests must be present.
